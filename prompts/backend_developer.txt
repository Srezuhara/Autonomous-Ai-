DEPENDENCY RULE: a FastAPI dependency is a PLAIN generator function. Never
decorate it with @contextmanager, and never wrap it in a helper that returns it.

  ❌ WRONG — injects the context-manager object, so every handler raises
     "'_GeneratorContextManager' object has no attribute 'query'":
      @contextmanager
      def get_db():
          conn = sqlite3.connect(DB_PATH)
          try:
              yield conn
          finally:
              conn.close()

      def _get_db():           # wrapper is just as broken
          return get_db()

      @router.get("/tasks")
      def list_tasks(db = Depends(_get_db)): ...

  ❌ ALSO WRONG — re-declaring the dependency in routes.py and yielding the
     result of calling the real one. Calling a generator function returns a
     GENERATOR, so every handler raises
     "'generator' object has no attribute 'execute'":
      from crud import get_db as crud_get_db

      def get_db():
          conn = crud_get_db()   # this is a generator, not a connection
          try:
              yield conn
          finally:
              conn.close()

  ✅ RIGHT — FastAPI manages the generator itself:
      def get_db():
          conn = sqlite3.connect(DB_PATH, check_same_thread=False)
          try:
              yield conn
          finally:
              conn.close()

      @router.get("/tasks")
      def list_tasks(db = Depends(get_db)): ...

THREAD RULE: every sqlite3.connect(...) that a request will use must pass
check_same_thread=False. FastAPI runs a plain `def` dependency in a worker
thread and the handler on another (always, for an `async def` handler), and
sqlite3 refuses a connection from a thread that did not create it: every such
request raises "SQLite objects created in a thread can only be used in that
same thread". This shipped: row 2 (2026-09-10) lost five of eight endpoints to
it. It applies to EVERY helper that opens a connection — if two modules each
define a get_connection(), both need it; better, define it once and import it.

Define the dependency once, in the module that owns the database, and import it
where it is used. Do not import it inside a function body, and do not write a
second `get_db` in routes.py — import the one that already exists and pass it
straight to Depends(...). If you find yourself calling a function that contains
`yield`, stop: that is FastAPI's job, not yours.

STARTUP RULE: schema creation must run on the APP, never on the router.
`@router.on_event("startup")` DOES NOT FIRE for a router that is included with
app.include_router(...), so the tables are never created and every read endpoint
returns 500 with "no such table". This shipped: matrix row 3 (2026-08-28) had
twelve dead endpoints and a perfectly good init_db() that nothing ever called.

  ❌ WRONG — silently never runs:
      @router.on_event("startup")
      def startup():
          init_db(sqlite3.connect(DB_PATH))

  ✅ RIGHT — a lifespan handler on the app, in main.py:
      from contextlib import asynccontextmanager

      @asynccontextmanager
      async def lifespan(app: FastAPI):
          conn = sqlite3.connect(DB_PATH)
          init_db(conn)
          conn.close()
          yield

      app = FastAPI(lifespan=lifespan)

Do not create tables at module level either: importing a module must not open a
database connection.

RESPONSE MODEL RULE: anything named in `response_model=` must be a Pydantic
BaseModel. A plain class raises FastAPIError while the module is being imported,
which takes the whole app down — not one endpoint, all of them. This shipped
too: row 2's services.py defined `class BookmarkOut:` with an `__init__`, and
routes.py used it as `response_model=List[BookmarkOut]`, so the app never booted.

  ❌ WRONG:
      class BookmarkOut:                 # services.py
          def __init__(self, id, url): ...

  ✅ RIGHT:
      class BookmarkOut(BaseModel):      # models.py or schemas.py
          id: int
          url: str

If a class is used as a response_model, it belongs with the Pydantic models and
it subclasses BaseModel. Never annotate a route with a hand-written class.

PYDANTIC VERSION RULE: this project installs pydantic 2.x. Write V2, never V1.
V1 config keys are not rejected under V2 — they are IGNORED, with only a warning
buried in stderr. `orm_mode` is the one that keeps shipping: it is silently
dropped, so `from_attributes` is never set, and every response_model that has to
serialize a database row or ORM object then raises a 500 at REQUEST time. The
module imports perfectly, so the import check sees nothing wrong. Twenty of
these shipped on 2026-08-29.

  ❌ WRONG:
      class ProductRead(BaseModel):
          id: int
          class Config:
              orm_mode = True            # ignored under V2

  ✅ RIGHT:
      class ProductRead(BaseModel):
          id: int
          model_config = ConfigDict(from_attributes=True)

Import `ConfigDict` from pydantic. The renamed keys are `orm_mode` →
`from_attributes`, `schema_extra` → `json_schema_extra`, and
`allow_population_by_field_name` → `populate_by_name`. Use `.model_dump()` in
place of `.dict()`, and `@field_validator` in place of `@validator` — the V2
validator takes the value and returns it, and is a `@classmethod`.

WIRING RULE: a route that needs data must reach the data layer. Declare the
dependency with Depends(...) and call a real method on it. Do not instantiate a
new Database() inside the handler body, and do not leave the injected object
unused. Keep the response shape consistent with the Pydantic model you declared
— if the model has `title`, the query must supply `title`, not `task_name`.

MODELS RULE: models.py is a flat file with Pydantic classes only. No database code.

Every name another file reads off models must EXIST in models.py. This is the
one that killed a whole build: routes.py was written against

    def create_supplier(supplier: models.SupplierCreate): ...
    def create_product(product: models.ProductCreate): ...

and models.py contained only SQLAlchemy ORM classes — Base, Supplier, Product,
Warehouse — and not one of the four *Create schemas. Python raises AttributeError
while routes.py is being imported, so every endpoint died, not just the writes.

  ❌ WRONG:
      # models.py
      class Supplier(Base):              # an ORM class
          __tablename__ = "supplier"

  ✅ RIGHT:
      # models.py
      class SupplierCreate(BaseModel):   # what a POST/PUT body parses into
          name: str
          contact_email: str | None = None

      class SupplierRead(SupplierCreate): # what response_model returns
          id: int

An ORM class cannot be used as a FastAPI body annotation or a response_model.
Before you finish routes.py, read back every `models.X` you wrote and confirm
models.py defines X. If a route accepts a JSON body, models.py has a schema for
it — an API with POST/PUT routes and no Pydantic models is always wrong.
